## 1. macOS sheet catalog vs. the owner's rule
Rule: *"prefer windows over modal sheets unless there are clear state-based justifications for sequencing user actions."*
Classification: **(a)** justified modal · **(b)** should be a window · **(c)** borderline.

### (b) Should be windows — browsable/reference content (8 items, 14 call sites)

| # | Sheet | Call sites | Justification for conversion |
|---|---|---|---|
| B1 | **Archival Neighbors** (`ArchivalNeighborsSheet`) | `App/SearchSheet.swift:182`, `App/SupportingViews.swift:3717`, `Browser/CompilationView.swift:124,134`, `CrossReference/CrossReferenceGraphView.swift` (archivalNeighborsTarget) | A results *list* of cross-volume documents the researcher wants to work through one by one. Tapping a row navigates → sheet dismisses → provenance context is lost; user must re-open and re-run the query per document. A `frus.archivalNeighbors` Window + `pendingBrowseDocument` hand-off keeps the list alive beside the reading window. The sheet's own overflow row even says "open Source Explorer to see them all" (`SourceExplorer/ArchivalNeighborsSheet.swift:104-109`) — it already aspires to a window. |
| B2 | **Cross-Volume Provenance** (`VolumeSourcesCrossVolumeSheet`) | `App/SupportingViews.swift:3728`, `Browser/CompilationView.swift:145` | Read-only reference answering "which other volumes drew on this collection?" — the archetype of content read *alongside* browsing those volumes. Rows aren't even tappable today (`Browser/VolumeSourcesView.swift:306-320`); as a window with navigable rows it becomes an actual research tool. |
| B3 | **NARA Catalog Lookup** (`NARACatalogLookupView`) | `App/MainWindowView.swift:101`, `App/MacDocumentView.swift:1019` | Live catalog search with browsable results; users will want it open while reading the source note that prompted it. The Source Explorer *window* (`frus.sourceExplorer`) already owns NARA integration — either fold this into that window or give it its own scene. Modal here means you cannot see the document text you're checking the citation against. |
| B4 | **Citation Lookup** (⌘⇧F, `CitationLookupView`) | `App/MainWindowView.swift:159`, `App/SearchSheet.swift:186` | Two-phase find flow with a result list and in-sheet `NavigationStack` push (`Citation/CitationLookupView.swift:65+`). Its sibling, full-text Search (⌘F), *is* a window. Inconsistent: both are "find a document" entry points. A `frus.citationLookup` Window (or a mode of the Search window) keeps parsed matches around while reading. |
| B5 | **People index** (corpus browser) | `App/SupportingViews.swift:2889` | Wraps the entire `PersonIndexView` browser in a modal — and person taps open a *second* sheet stacked on it (`Browser/PersonIndexView.swift:224` via `selectedIndexEntry`). Reference content, cross-volume, with merge-correction workflows; belongs in a window (or a sidebar section of the corpus-browser window). |
| B6 | **Volume connection graph** | `App/SupportingViews.swift:3003` | A browsable graph — the app already has a Cross-Reference Graph *window* precedent (`frus.crossReferenceGraph`). Same visual-encoding contract, same "explore alongside documents" use. |
| B7 | **While-Indexing research guide** (`WhileIndexingSheet`) | `App/SupportingViews.swift:1095` (auto-presents 0.6 s after indexing starts) | Auto-popping a modal interrupts whatever the user was doing. macOS already has the `frus.researchGuide` Window (`App/FRUSExplorerApp.swift:615`); the indexing banner should offer a click-through to that window instead of self-presenting a modal. |
| B8 | **Collection entry inspector** | `Collections/MacCollectionManagerView.swift:1221` (`MacEntryRow`), `Collections/CollectionEntryRows.swift:583,163` | Notes/highlights/tags/provenance reference for an entry — on iPad the analogous surface is a system `.inspector`; on macOS it's a modal sheet that blocks the outline you're editing against. Convert to `.inspector` on the Collections window (or a popover anchored to the ⓘ button). Its "Insert as Excerpt" action *edits the outline* — doing that blind from a modal is exactly the sequencing problem the rule targets. |

## 2. Top-20 prioritized UX gaps

1. **Archival Neighbors modal loses context on every navigation** — convert to window (B1). `App/SearchSheet.swift:182` et al.
2. **Note-writing blocks reading the document** on macOS (C1). `App/MacDocumentView.swift:221`.
3. **No Format menu → rich-text bold/italic likely dead on macOS.** The app's `.commands` (`App/FRUSExplorerApp.swift:683-726`) never adds `TextFormattingCommands()`; `NSTextView` bold/italic key equivalents (⌘B/⌘I) are menu-driven, and `RichTextEditor`'s doc comment promises them (`Collections/CollectionRichTextEditor.swift:147-149`). Without the menu, formatting is reachable only via the right-click Font submenu. One-line PR: add `TextFormattingCommands()` to `.commands`. **Verify in-app.**
4. **No rich-text formatting affordance on iOS at all** — `UITextView.allowsEditingTextAttributes` edit-menu only (`CollectionRichTextEditor.swift:221`); no B/I/U toolbar above the keyboard. Discoverability ≈ zero for the flagship authoring feature. PR: `inputAccessoryView`/`keyboardToolbar` with Bold/Italic/Underline.
5. **No menu-bar commands for collection authoring.** Commands cover About / Research Guide / Citation Lookup / History only (`App/FRUSExplorerApp.swift:683-726`). Missing: File ▸ New Collection (⌘N), Export Collection (⌘E), Add Documents (⌘⇧A exists only as a button shortcut inside `MacCollectionManagerView.swift`), toggle preview pane, Edit ▸ Add Heading/Prose. A `CommandMenu("Collection")` gated on the Collections window being key would ride existing infra.
6. **Keyboard-shortcut coverage is thin overall**: 8 non-default shortcuts app-wide (5 window scenes + ⌘⇧F + ⌘⌥R + ⌘⇧A). No shortcuts for: next/previous document, add note (⌘⇧N), highlight selection, toggle research panel, toggle preview. For a document-reading app this is the biggest macOS-power-user gap.
7. **Citation Lookup (⌘⇧F) is a sheet while Search (⌘F) is a window** — inconsistent mental model for the two find flows (B4). `App/MainWindowView.swift:159`.
8. **Collections entry inspector: modal sheet on macOS vs `.inspector` on iPad** (B8) — same content, opposite idioms. `Collections/MacCollectionManagerView.swift:1221`.
9. **Auto-presented WhileIndexing modal** interrupts first-run exploration on macOS (B7). `App/SupportingViews.swift:1088-1097`.
10. **Advanced filters modal hides the results being filtered** (C4). `App/SearchSheet.swift:176-181`.
11. **Sheet chrome inconsistency on macOS**: codebase's own rule says NavigationStack-in-sheet renders sidebar-style chrome (`App/SupportingViews.swift:542`, `CollectionEditorView.swift:333-335`) and uses VStack+bottom-Done for some sheets, yet `ArchivalNeighborsSheet`, `VolumeSourcesCrossVolumeSheet`, `PersonIndexDetailSheet`, `CitationLookupView` still ship NavigationStack+toolbar-Done on macOS (`SourceExplorer/ArchivalNeighborsSheet.swift:80-140`, `Browser/VolumeSourcesView.swift:306-345`). Pick one pattern; also Done placement varies (toolbar `.confirmationAction` vs bottom-right button bar).
12. **Cross-volume provenance rows are dead ends** — volume names aren't tappable (`Browser/VolumeSourcesView.swift:306-320`); a researcher must memorize the volume id and browse to it manually. Make rows navigate (and see B2).
13. **iPhone editor pane toggle at top of screen** — the Outline|Preview segmented control (`Collections/CollectionEditorView.swift:535-547`) sits in the hardest reach zone and costs ~44 pt of the smallest screens; a bottom `safeAreaInset` bar (as `CollectionAddDocumentsSheet.swift:578-588` already does for its Add button — good pattern) or a toolbar `ToolbarItemGroup(.bottomBar)` would fit iPhone ergonomics.
14. **3-deep modal stack on iPhone**: Document → Collection editor sheet → Add Documents sheet (all `.large` detents), each with a different dismiss affordance (Done / Cancel / swipe). `Collections/CollectionEditorView.swift:444-450,483`.
15. **Word Cloud / Analytics / Chronology are sheets on iPad** (`App/MainTabView.swift` pendingWordCloud sheet; `Browser/BrowserView.swift:168+`) even though iPad has Stage Manager scenes for documents/graph/source explorer — iPhone hand-me-down on a platform with window idioms. Consider `openWindow` on iPad where supported.
16. **Cross-Reference Graph window defaultSize 480×440** (`App/FRUSExplorerApp.swift:526`) is cramped for a graph canvas + legend; Source Explorer had the same class of bug fixed in Session 94 (comment at `FRUSExplorerApp.swift:82-83`).
17. **Preview cap "Render All" state is per-session but invisible** — `previewRenderAll` hoisted (`CollectionEditorView.swift:178-180`) yet nothing in the UI indicates the preview is truncated after toggling panes; the cap notice lives only inside the web content (`Collections/CollectionPreviewView.swift:238,355`).
18. **`.help()` tooltips are broadly good (142 uses) but uneven on new authoring controls** — e.g. the iPad preview/inspector toolbar buttons have a11y labels but no `.help` for iPad-pointer/Catalyst hover (`CollectionEditorView.swift:646-663`), while macOS manager buttons have `.help` but rely on symbol names for VoiceOver (`MacCollectionManagerView.swift:1178-1216`).
19. **Main window minWidth 980** (`App/FRUSExplorerApp.swift:638`) exceeds a split-screen half of a 13″ MacBook Air (≈722 pt) — the window can't be tiled side-by-side with anything on small displays; the toolbar-overflow rationale is documented but a `.toolbar(removing:)`/priority approach would degrade more gracefully.
20. **Excerpt rows show no volume title fallback context in iOS swipe-delete flows** and generated rows are opaque ("Apparatus" glyph + name only, no preview) — minor, but the outline's newest row types give less orientation than document rows (`Collections/CollectionEntryRows.swift:293-360, 362-430`).

## 3. Accessibility gaps, ranked by severity

**Baseline counts** (grep): `accessibilityLabel` 194, `accessibilityHint` 22, `accessibilityValue` 4, `accessibilityElement` 19, traits/actions/rotor 38, `.help` 142, `Image(systemName:)` 241, **`.font(.system(size:))` 344**, `dynamicTypeSize`/`ScaledMetric` **1**, `@FocusState`/`focusable` **2**, `differentiateWithoutColor` **0**, contrast/transparency env **0**. Reduce-motion: handled in both graph views + word cloud (good).

### Severity 1 — blocking for some users
- **A1. Dynamic Type is effectively unsupported on key iOS surfaces.** 344 fixed-point fonts; only one scaled metric app-wide. Worst iOS-visible offenders: `Onboarding/OnboardingView.swift` (5), `App/IndexingBannerView.swift` (6), `App/IndexingQueueBannerView.swift` (8), `DocumentView/DocumentView.swift` (4), plus 22 fixed `.frame(height:)` sites. Mitigation (PR-sized per file): replace `.system(size:)` with text styles or `@ScaledMetric`; audit the 22 fixed heights with AX5 sizes. (The 145 in `Settings/FRUSSettingsView.swift` and 72 in `App/SupportingViews.swift` are macOS-only — lower priority but not exempt on macOS 14+ text scaling.)
- **A2. Rich-text prose editor ignores Dynamic Type on iOS.** `UITextView` gets a one-shot `preferredFont(forTextStyle: .callout)` and never sets `adjustsFontForContentSizeCategory = true` (`Collections/CollectionRichTextEditor.swift:219-227`); RTF round-trips concrete fonts, so even relaunching doesn't rescale existing prose. Mitigation: set `adjustsFontForContentSizeCategory`, and map stored fonts through `UIFontMetrics` at display time. Also: the fixed-height iOS highlight-picker detent `.presentationDetents([.height(180)])` clips at large type (`DocumentView/DocumentView.swift:1825`).
- **A3. macOS highlight color picker is a color-only, label-free control.** Plain circle buttons with only `.help(color.rawValue.capitalized)` — unlocalized, and no `accessibilityLabel`, so VoiceOver reads nothing meaningful (`App/SupportingViews.swift:497-514`). iOS variant has labels but also unlocalized `color.rawValue.capitalized` (`DocumentView/DocumentView.swift:1808`). Mitigation: use `DocumentHighlight.Color.displayName` (`Models/DocumentHighlight.swift:185`) for both label and help, add a shape/initial glyph for `differentiateWithoutColor`.

### Severity 2 — major friction
- **A4. VoiceOver cannot reorder the collection outline.** Reorder is `onMove` drag-handles behind `EditButton` on iOS (`Collections/CollectionEditorView.swift:992,1070`) and raw drag on macOS (`MacCollectionManagerView.swift:718`); context menus offer indent/outdent/delete but no Move Up/Down (`Collections/CollectionEntryRows.swift:189-232`). Mitigation: add `.accessibilityAction`s (and context-menu items) for Move Up / Move Down on every row type — one PR, shared helper next to `structuralDeleteButton`.
- **A5. Selection state conveyed only by SF-symbol swap** (checkmark.circle vs circle) with no `.isSelected` trait or `accessibilityValue`: `Collections/CollectionAddDocumentsSheet.swift:1349`, `Settings/FRUSSettingsView.swift:555,1950,2322`, `Onboarding/OnboardingView.swift:538`, `Onboarding/DownloadScopePickerView.swift:295`. Mitigation: `.accessibilityAddTraits(isSelected ? .isSelected : [])` at each site.
- **A6. Stateful icon toggles have static labels.** iPad preview toggle always reads "Show live preview" whether on or off (`Collections/CollectionEditorView.swift:650-653`); same for the details-inspector toggle (659-662) and Zotero key reveal eye (`Settings/FRUSSettingsView.swift:2636`). Mitigation: flip the label with state or add `accessibilityValue("on"/"off")`.
- **A7. macOS keyboard navigation of custom rows.** Only 2 focus-API uses app-wide. Entry rows in the Collections manager are `buttonStyle(.plain)` HStacks inside a `List` without selection — arrow keys do nothing; actions need Full Keyboard Access (`Collections/MacCollectionManagerView.swift:1071-1218`). Same for search-result rows (`App/SearchSheet.swift:979+`). Mitigation: `List(selection:)` + return-key open, or `.focusable()` rows with `.onKeyPress`.

### Severity 3 — polish
- **A8. Sentiment word-cloud lens and export are color-only encodings** (`Analytics/WordCloud/WordCloudExport.swift:84-105`); no `differentiateWithoutColor` fallback anywhere in the app. Mitigation: honor `@Environment(\.accessibilityDifferentiateWithoutColor)` — add +/− prefixes or underline in the sentiment lens.
- **A9. Preview WKWebView semantics**: generated HTML has fixed pt sizes, and the "Render All" cap notice lives inside the web content only (`Collections/CollectionPreviewView.swift:238-358`); VoiceOver users get no container label saying it's a live preview of the outline. Mitigation: `accessibilityLabel` on the web view container; respect `-apple-system` dynamic sizes in preview CSS.
- **A10. `structuralDeleteButton` has `.help` but no explicit label** (`Collections/CollectionEntryRows.swift:239-247`) — SF "trash" name saves it, but localized `accessibilityLabel("Remove entry")` is a two-line fix. Similarly graph controls flagged by scan: `CrossReference/CrossReferenceGraphView.swift:1137,1287,1429,1715`.
- **A11. Positive precedents to copy** (for consistency, not fixes): `controlHelp` combined a11y+tooltip modifier (`DocumentView/DocumentView.swift:913-919`), graph `accessibilityRepresentation` list (`CrossReference/CrossReferenceGraphView.swift:361-437`), excerpt color chips with `displayName` labels (`Collections/CollectionEntryRows.swift:323`).
