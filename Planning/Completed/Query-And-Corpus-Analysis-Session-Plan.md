# Query & Corpus Analysis — Session Plan

**Date:** 2026-07-24
**Execution context:** local Mac + Xcode (not a cloud container). Every session below is
buildable, runnable, and verifiable on the owner's machine against a real indexed corpus.

**Provenance.** Two externally-produced FRUS research reports — *"Drawing the Line"*
(American responsibility for allied military security, 1945–51) and *"Nothing Will Be Said
Here"* (off-shore procurement, 1950–72) — were generated by an agent working directly
against a tokenized FRUS corpus in a local SQL database. A transferability assessment
(2026-07-24) established that **the reports' entire evidentiary apparatus is SQLite FTS5
work this app can host**: phrase rarity counts, proximity sweeps, per-year distributions,
absence testing, and deterministic verbatim quote-checking. Only the *authorship* of the
reports — cross-document synthesis over ~190 verified passages — exceeds the on-device
model (`AppleIntelligenceProvider.contextWindowTokenLimit = 3_072`). Nothing in the
reports is bounded by device compute.

**The diagnosis this plan acts on.** The app is very good at *finding a document* and has
almost nothing for *characterizing a set*. Every analytic today takes a **term** and shows
its distribution (`CorpusAnalyticsService.termFrequencyByYear`), or takes a **document**
and shows its neighbours (`RelatedDocumentsEngine`, six weighted axes). Nothing takes the
400 results on screen and reports what they collectively contain. Two enabling moves
unlock the rest: **make the query legible**, and **make the result set a first-class
object**.

**Scope of this plan:** 13 sessions in 5 milestones. Each milestone is a coherent stop
point — you can ship after any one of them and the app is better, not half-built.

House conventions followed: each session is 1–2 PRs with goal, file-anchored deliverables,
data/migration dependency, prerequisites, effort, decision points, and an explicit
on-device verification step. **Line/symbol anchors are from the 2026-07-24 audit and must
be re-verified at each session's start** — search-adjacent code moves.

## How to run these sessions on the Mac

**Branch per session.** `claude/qa-<session-id>-<slug>`, one or two PRs each. Do not stack
sessions on one branch — the milestones are independently shippable by design.

**Fast loop (Milestone 1 is mostly this).** `FTS5Store` source files compile *directly into
the app* (`project.yml:67`), not via SPM product linkage, so the same files are covered by
the SPM test target and shipped in the app:

```bash
swift test --filter FTS5StoreTests          # seconds; no simulator, no Xcode UI
swift build                                  # generators + FTS5Store
```

`FTS5StoreTests/FTS5InlineQueryParserTests.swift:345` already creates a **real** FTS5 table
(`tokenize='porter unicode61'`) and runs rendered expressions through SQLite — so parser
work is verified against the actual engine, not a mock. Extend that harness rather than
adding a new one.

**App test loop.**

```bash
xcodebuild test -project FRUSExplorer.xcodeproj -scheme FRUSExplorer \
  -destination "platform=iOS Simulator,name=iPhone 17"

xcodebuild test -project FRUSExplorer.xcodeproj -scheme FRUSExplorer \
  -only-testing FRUSExplorerTests/IndexingPipelineTests

xcodebuild test -project FRUSExplorer.xcodeproj -scheme FRUSExplorerMac \
  -destination "platform=macOS"
```

**Adding new source files.** `project.yml` declares directory globs
(`- path: FRUSExplorer`), so a new `.swift` file in an existing directory is **not** in the
Xcode project until you regenerate:

```bash
xcodegen generate --spec project.yml
git checkout -- FRUSExplorer.xcodeproj/xcshareddata/xcschemes/   # ALWAYS — xcodegen destroys these
```

Sessions below flag **“needs xcodegen”** where they add files. Sessions that only edit
existing files do not.

**Corpus for realistic verification.** These features are meaningless against three indexed
volumes. Before Milestone 2, index a substantial slice on the Mac — the whole corpus is 552
volumes / ~3.34 GB of TEI (`FRUSExplorer/Resources/manifest.json`), which is unremarkable
on a Mac and the right target for facet/keyness performance work. Where a session has a
performance gate, it states the corpus size the gate assumes.

**Where the reports are the test oracle.** Several sessions can be verified by reproducing
a published number from the two reports. Those are called out under **Verify** — they are
the highest-value regression checks available, because they were produced independently of
this codebase.

## Cross-cutting guardrails (every session)

- **No index migration in Milestone 1.** NEAR is a query-language feature over the existing
  index, and `fts5vocab` is a read-only virtual table over FTS5's own b-tree. Neither
  touches stored data, so neither triggers a reindex. Preserve that property — it is what
  makes Milestone 1 shippable without a migration story.
- **External-content FTS5 is the constraint to respect.** `frus_documents` is
  `content='document_cache'` (`FTS5Store/FTS5Types.swift:107`); column values are read from
  `document_cache` at query time and the trigger set keeps them in sync. Anything that
  needs raw text reads `document_cache.body_text` (`IndexingPipeline.swift:3884`) — never
  reconstruct text from the index.
- **Search and analytics must not diverge.** Both paths already share
  `FTS5InlineQueryParser` (`CorpusAnalyticsService.makeQuery`, line 361, exists precisely
  because they once diverged and analytics over-reported phrase queries). Any new query
  capability lands in the shared parser/renderer, never in one caller.
- **No silent truncation** (house style). `FTS5Store.matchedDocumentKeys` caps at 500,000
  rows (`FTS5Store.swift:350`); facet and keyness passes will introduce their own bounds.
  Every bound must be surfaced in-UI when hit, never quietly applied.
- **Counts need denominators.** The source reports' weakest methodological move is raw
  counts with no baseline. `documentTotalsByYear`/`ByDecade` already exist
  (`CorpusAnalyticsService.swift:708`). Ship the better version.
- **Indexed-scope honesty.** "0 results corpus-wide" in this app means "0 in what I have
  indexed." Any absence-flavoured feature must state its denominator in-UI.
- **Standing gates:** `String(localized:)` for all user-facing strings; doc comments on
  every `public`/`internal` symbol; Apache headers on sources *and* tests; `Version history`
  bumps on allowlisted files; `CodingStandardsAuditTests` green; iOS **and** macOS parity
  (dual-manager surfaces); docs rider per feature session (Research Guide /
  `IndexingEducationView`).

# Milestone 1 — The query becomes legible

*Three sessions. No index migration. Ships alone.* After this milestone a researcher can
see what their query actually did, why it returned nothing, and what the stemmer silently
did to their terms.

## Q-1 — `NEAR` proximity operator *(Effort S)*

**Goal.** Expose FTS5's `NEAR` through the shared parser and renderer. This is the single
capability the reports use that the app cannot express at all — the alliance report's
central claim (that "aid" and "guarantee" were genuinely distinct categories) rests on
`NEAR("military guarantee" Europe, 30)` returning 0/0/0/3 across 1945–48.

**Deliverables.**
- `FTS5InlineQueryParser` recognises `NEAR(a b, N)` / `NEAR("phrase" term*, N)` as a single
  opaque operand, folded into the existing `classify` / `demoteOrphanedOperators` /
  `assemble` pipeline exactly as a parenthesised group already is. Case-insensitive on
  input (matching `AND`/`OR`/`NOT` handling), **rendered uppercase** — FTS5 requires
  operator keywords uppercase.
- Operand rules enforced and documented: NEAR operands may be terms, phrases, or prefix
  terms **only** — `AND`/`OR`/`NOT` cannot nest inside. A malformed NEAR degrades to
  literal search words (the established graceful-degradation contract), never to invalid
  FTS5.
- Default `N = 10` when the distance is omitted, matching FTS5.
- `FTS5Query.sanitizeTerm` (`FTS5Query.swift:243`) currently strips `(`, `)`, `/`, `:`, `*`
  — it must not eat a NEAR the parser has already recognised. Keep sanitisation for bare
  text; exempt the pre-rendered operand.
- Column scoping: the prefix must wrap the **whole** `NEAR(...)`, not each inner operand
  (`{body_text} : NEAR(a b, 5)`). `SearchService.renderExpression` (line 231) applies
  prefixes per operand today — verify the NEAR path.
- `SearchService.positiveTerms` (line 284) must not emit `NEAR` as a highlight term, or the
  snippet highlighter will bold the literal word.
- Update the syntax table in `FTS5Query.swift:13-28` and **delete the stale limitation note
  at line 26** ("Near operators are not exposed; add to a future version if needed").
- Tests in `FTS5StoreTests/FTS5InlineQueryParserTests.swift` against the real FTS5 table at
  line 345: distance semantics, phrase operands, prefix operands, nesting rejection,
  case-insensitivity, degradation, column scoping.

**Data & migration:** none. Query-side only.
**Prereq:** none. **Needs xcodegen:** no.

**Decision point (Q-1-1).** Surface syntax for the distance. FTS5's own comma form
(`NEAR(a b, 20)`) is what the reports use and what a researcher will paste from published
method appendices — recommended. A friendlier `a NEAR/20 b` infix (SQLite's older FTS3/4
form) is more typeable but diverges from the engine and from history.state.gov. Lean:
support the canonical comma form, and accept `NEAR/N` as an alias if it is cheap.

**Verify.** `swift test --filter FTS5StoreTests`, then in the app against an indexed
1945–51 slice, reproduce the report's published counts:
`NEAR("military guarantee" Europe, 30)` → 0 (1945), 0 (1946), 0 (1947), 3 (1948).
A mismatch here is a real finding either way — it means the app's indexed scope or the
report's corpus differs, and you want to know which before building on top.

## Q-2 — Query Inspector *(Effort M)*

**Goal.** Make the query a legible instrument. Today the rendered FTS5 expression is
invisible, and a zero-result query reports only "Try different keywords or adjust your
filters" (`SearchView.swift:612` results section) — which is indistinguishable from a typo,
a stemming surprise, and a genuine historical absence.

**Deliverables.**
- An inspector surface (macOS: an inspector pane or popover on the search field; iOS: a
  disclosure below the field) showing:
  - the **rendered FTS5 MATCH expression** — `SearchService.makeMatchExpressions` (line 196)
    already produces it and discards it after use;
  - **per-operand hit counts** within the current filter scope;
  - each term's **Porter stem** (`PorterStemmer.stem` is already in-app and used for
    snippet highlighting at `SearchService.swift:113`).
- **Zero-result decomposition.** When a conjunctive query returns nothing, run each operand
  separately and report which conjunct is empty. Cost is *n* extra `searchCount` calls
  (`SearchService.swift:153`) — cheap and only on the zero path.
- **Live operand counts while building.** `SubjectCategoryFacetPicker` already shows
  "reach" counts per facet (`SearchFilterView.swift:1173-1187`) — the right instinct,
  generalised to every operand and filter. Debounced.
- The inspector is the app's query documentation: no separate help screen. A researcher
  learns `NEAR` by watching the expression change.

**Data & migration:** none.
**Prereq:** Q-1 (so the inspector explains NEAR from day one).
**Needs xcodegen:** yes (new view files).

**Decision point (Q-2-1).** Where the counts come from. Reusing `searchCount` per operand
is exact and honest but is *n* round trips on every keystroke-debounce; a single
`fts5vocab`-backed corpus estimate (Q-3) is one lookup but ignores the active filter scope.
Lean: exact `searchCount` in the *scoped* inspector, `fts5vocab` for the unscoped
type-ahead estimate — and label which is which, since a scoped and unscoped count differing
is itself information.

**Decision point (Q-2-2).** Whether the raw FTS5 expression is always visible or behind a
"show technical detail" toggle. Lean: visible. The audience is researchers who publish
method appendices; hiding it optimises for the wrong user.

**Verify.** Type `containment` and confirm the inspector shows the stem `contain` with a
corpus count in the thousands (the report's documented trap). Type a deliberately
over-constrained conjunction and confirm the empty conjunct is named.

## Q-3 — Corpus vocabulary (`fts5vocab`) + stem transparency + exact-word filter *(Effort M)*

**Goal.** Give the app a corpus-wide term dictionary it currently lacks, and close the
stemming trap both reports flag as their most dangerous failure mode.

**Deliverables.**
- A `fts5vocab` virtual table over `frus_documents` in `'row'` mode
  (`CREATE VIRTUAL TABLE … USING fts5vocab('frus_documents','row')`), created alongside the
  existing schema in `FTS5Store.createSchema`. It yields `(term, doc, cnt)` — **document
  frequency and total occurrences per index term, corpus-wide, with no scan and no added
  storage.** The app uses `fts5vocab` nowhere today.
- This lands the **occurrences-vs-documents distinction** for free at corpus grain — 200
  occurrences across 150 documents is a pattern; 200 across 3 is one memo with a tic. The
  existing analytics count documents (correct) but never say so.
- **Stem-collision warning** in the search field and inspector: "*containment* → **contain**
  — 12,431 documents; many are ordinary uses." One `fts5vocab` lookup.
- **Exact-word mode.** The stemmed result set is always a strict **superset** of exact-word
  matches, so an exact search is the stemmed query plus a word-boundary post-filter against
  `document_cache.body_text`. This is precise, needs no second index, and no reindex.
  Applies to result rows and to counts — a count that ignores the post-filter would be a
  silent lie.
- Works with external-content tables: `fts5vocab` reads the inverted index, not the content
  table, so `content='document_cache'` is not an obstacle.

**Data & migration:** a virtual-table `CREATE` only — **no reindex**, no data movement.
Idempotent, in the established `CREATE … IF NOT EXISTS` pattern.
**Prereq:** none (Q-2 consumes it, but the order can invert).
**Needs xcodegen:** yes if new store files are added.

**Decision point (Q-3-1).** `fts5vocab` terms are **stems**, not surface forms — so the
warning can say "*contain* matches 12,431 documents" but cannot list *containment /
contains / containing* without scanning `document_cache.body_text`. Lean: ship the
count-only warning now (free, and it is the part that prevents the error), and defer a
cached stem→surface-forms map to D-1 where the vocabulary explorer needs it anyway.

**Decision point (Q-3-2).** Whether exact-word mode is a per-query toggle or a per-term
sigil (e.g. `="containment"`). Lean: per-term sigil, because real queries mix — you want
`containment` exact but `polic*` stemmed in the same expression. A global toggle forces an
all-or-nothing choice the research doesn't have.

**Verify.** Reproduce the reports' stemming-trap figures against a fully indexed corpus:
`industrial = industry = industries = industrialization` collapsing to one stem, and
`production = productive = productivity` likewise. Exact-word mode on `containment` should
collapse a five-figure count to a plausible three-figure one.

# Milestone 2 — The result set becomes an object

*Three sessions.* After this milestone a researcher can ask what 400 hits collectively
contain, instead of reading them one row at a time.

## R-1 — Result-set facets *(Effort L — the anchor session)*

**Goal.** The single biggest win in the plan. Given the current result set, break it down by
year, volume/subseries, person, document type, and archival provenance — each facet
click-to-narrow. "Your 412 hits: 60% in three volumes, spiking in 1948, and Hickerson
appears in 31 of them" is the move from a list to a finding.

**Deliverables.**
- Facet aggregation in `IndexingPipeline` alongside `searchDocuments` /
  `searchDocumentsCount`, computed **in SQL over the match** — never by materialising every
  result row in Swift. All source tables are already indexed and joined by
  `(volume_id, document_id)`:
  - **Year / decade** — `document_dates` (`IndexingPipeline.swift:3859`, indexed on
    `date_iso`)
  - **Volume / subseries** — `document_cache.volume_id` + manifest
  - **Person** — `person_mentions` (line 3899), resolved through the cross-corpus rollup
    (`person_rollup`, line 3938) so a person isn't split across name variants
  - **Document type** — `is_editorial_note` / `is_front_matter` (already `SearchSQLFilters`
    dimensions)
  - **Archival provenance** — `document_sources` (line 4014); surface the honest coverage
    caveat, per house style
- Each facet row applies as a filter through the **existing** `SearchSQLFilters` fields —
  no new filter plumbing, so facets and the filter sheet cannot disagree.
- A facet panel: macOS inspector column; iOS a sheet or the existing filter surface. Follows
  the results/timeline toggle pattern already in `SearchView.swift:612`.
- Bounds surfaced, not silent: facet computation caps (top-N per facet, and any match-size
  ceiling) must be visible when hit.

**Data & migration:** none — all facet sources are already indexed.
**Prereq:** none strictly; far more useful after Q-1/Q-2.
**Needs xcodegen:** yes.

**Effort note.** L because of the SQL aggregation work and dual-platform placement, not
algorithmic difficulty. ~~Consider splitting into R-1a (year + volume + type…) and R-1b
(person + provenance…).~~

**[2026-07-29] Split differently, and here is why.** The suggested facet-group split would
build the panel UI twice while barely reducing risk — all five aggregates are the same
shape (`GROUP BY` over a materialised match set), and the Q-M2 measurements showed the
per-facet cost spread is small once the covering index exists. The bulk of the effort is
the dual-platform placement, exactly as the effort note says. So:

- **R-1a — facet aggregation** (headless): the TEMP match set, all five aggregates, the
  bounds, coverage caveats. Acceptance is `EXPLAIN QUERY PLAN` per the Q-M2 rule.
- **R-1b — macOS inspector column.**
- **R-1c — iOS sheet.**

This is the shape that worked for Q-2 (model then surfaces) and Q-3 (data layer then
feature): the correctness lands in a PR where it can be measured and mutation-tested, and
the UI is then built once against a proven aggregate.

**Decision point (R-1-1).** Facet computation timing: eagerly with every search (adds
latency to every query) vs. lazily when the panel opens (a second pass over the same
match). ~~Lean lazy, with the year facet eager — it is cheap and it feeds the timeline view
that already exists.~~

**[2026-07-29] Answered: lazy for ALL sections, including years — the eager-years rationale
rests on a false premise.** The existing timeline is *not* fed by a facet: it is built
client-side from `vm.displayedResults` (`SearchView.swift:758-762`), so an eager year
aggregate would be a second, redundant source rather than a shared one. And years is not
free — measured at **0.44 s** over 195,613 matches on the real store, which is real latency
to add to every search for a panel most searches never open. Lazy per section, computed on
first open, cached per match set.

**Decision point (R-1-2).** Whether facet counts respect the checklist-mode hidden set
(`vm.displayedResults` vs `vm.results`, `SearchViewModel.swift:262`). Lean: facets describe
the *whole* match, with a note when checklist mode is hiding rows — otherwise the
denominator shifts under the researcher as they triage.

**Verify.** Against an indexed 1946–50 slice, search `offshore procurement` and confirm the
volume facet concentrates as the procurement report describes (peak 1951–53, thinning
sharply by 1959).

- **PR-C** — dispersion from `volumeDataByTerm`/`subseriesDataByTerm`: date-independent, zero

  whose sum is being decomposed, never `matchedDocumentCount`.
- **PR-D** — per-period occurrences via a `'instance'`-mode `fts5vocab` companion. Bucket in
  Swift with the same fallback as the numerator, or undated documents' occurrences vanish while
  their documents remain — the mirror image of the CA-4 bug. Occurrence counts are **not**
  honest for every query shape: exact-word is impossible from a stemmed index, 3+-operand NEAR
  is not expressible, and booleans have no single honest total. Suppression must be an explicit
  state with a reason, never a zero or a blank cell.

  ### PR-D measurement pass — 2026-07-30, on the real 6.3 GB index

  Measured read-only (`mode=ro`) before designing, because the cost estimates in this plan were
  extrapolated from a 20k-document replica. **Feasible, and the shape is settled — but not the
  shape that was assumed.**

  **Corpus:** 274,927 distinct stems, **234,155,358 postings**, 316,839 documents.

  **1. No persistent DDL is needed.** A `TEMP` instance-mode companion attaches to the read-only
  main database in **6 ms**:
  `CREATE VIRTUAL TABLE temp.v USING fts5vocab('main','frus_documents','instance')`.
  That removes the whole schema-lifecycle problem this plan budgeted for: no migration, no
  generation bump, no DDL at `FTS5Connection.swift:131/:159`, no matching DROP at `:155`, and no
  stale-companion-after-reindex risk (#275's pattern). The companion cannot outlive the connection
  that made it. `fts5vocab` stores nothing either way — it reads the index.

  **2. The instance scan is fast; the JOIN was going to be the whole cost.** Aggregating
  `(doc, COUNT(*))` from the companion runs at **~7–8M postings/s**:

  | stem | postings | documents | vocab only | + SQL join to `document_cache` |
  |---|---|---|---|---|
  | `embargo` | 10,783 | — | 0.001 s | — |
  | `khrushchev` | 14,930 | — | 0.002 s | — |
  | `contain` | 57,596 | 39,496 | **0.017 s** | 2.00 s |
  | `nuclear` | 59,689 | 10,496 | — | 0.39 s |
  | `govern` | 985,733 | 195,519 | **0.140 s** | 8.99 s |
  | `state` | 1,688,186 | 299,557 | **0.233 s** | 12.91 s |
  | `the` (ceiling) | 16,767,406 | 314,609 | **2.03 s** | — |

  Cost tracks **document count, not postings**: `nuclear` (59,689 postings / 10,496 docs) takes
  0.39 s where `contain` (57,596 postings / 39,496 docs) takes 2.18 s. Nearly identical posting
  lists, 3.8× the documents, 5.6× the time. The cause is ~300k random rowid lookups into a table
  whose rows average 5.7 KB of `body_text`. Pre-aggregating per document before joining barely
  helps (14.29 s → 12.91 s for `state`) because the lookup count is what matters.

  **So do not join in SQL.** Read `(doc_rowid, occurrences)` from the companion and bucket in
  Swift. That is 40–90× faster on common terms and it is the difference between a usable feature
  and an unusable one.

  **3. The rowid → year map is nearly free, from an index added for something else.**
  `SELECT rowid, volume_id, document_id FROM document_cache` is served by a **covering index** —
  `idx_document_cache_facet`, added for R-1's facets — because every SQLite index entry carries
  the rowid. All 316,839 rows in **0.114 s**; joined through to `date_iso`, **0.243 s**. Build it
  once, cache it beside `allDocumentKeysWithDates()`.

  **4. Parity is exact.** For every term checked, instance-mode postings equal row-mode `cnt` and
  distinct instance docs equal row-mode `doc` (`allianc` 16,253/8,160 · `contain` 57,596/39,496 ·
  `guarante` 31,587/18,288 · `nuclear` 59,689/10,496). The two vocab modes agree, so the
  occurrence numerator can be checked against the cheap row-mode scalar in a test.

  **Budget, then:** ~0.24 s once for the map, plus 0.001–0.23 s per realistic research term. The
  pathological ceiling a researcher could type by accident is `the` at 2.0 s, which is long enough
  to want a progress state.

  **Still unmeasured, and stated as such:** iPhone. The design's dominant cost is now a sequential
  posting-list scan plus one covering-index pass, not 300k random reads into a 6.3 GB file, so the
  risk profile is far better than the rejected shape — but the 8 MB page cache and 128 MB mmap at
  `FTS5Connection.swift:77-82` are not a Mac's, and `the`-class terms deserve a device check before
  the progress state is designed away. Memory also wants a bound: `the` returns 314,609 rows.
- **PR-E** — surface the corpus-wide `occurrences` / `occurrencesPerDocument` that
  `SearchService.corpusDocumentFrequency` already fetches and discards. One property access
  plus a label, explicitly marked corpus-wide and unfiltered.

**Filed separately, not R-2:** the analytics cache is invalidated per *completed volume* while
the numerator MATCHes live, so a share can exceed 100% mid-index. That is an indexing-lifecycle
defect. **Do not clamp shares to 100%** — clamping is the one change that would hide it.

## R-3a — Two-phase fetch *(Effort M, infrastructure)*

**[2026-07-29] Added here deliberately, not as a standalone slot.** The Q-M2 prerequisite
work measured this as the largest remaining latency win in the app, and it has a genuine
dependency edge with R-3 — which is why it belongs immediately before it rather than
anywhere else in the plan.

**Goal.** Stop paying for `document_cache` before the sort. `searchDocuments` joins the fat
content table *then* applies `ORDER BY m.score` (`IndexingPipeline.swift:2035,2039`), so
every matched row is materialised before the sorter runs — 195,613 rows at ~5 KB of
`body_text` each for a common term. Rank narrow first, hydrate only the rows that survive.

**Measured on the real 6.3 GB store**, `"government"`, byte-identical output (42,569,775
bytes of body text either way):

| | today | two-phase |
|---|---|---|
| 7,500-row fetch | 10.46–10.62 s | **0.606 s** |
| first page (20 rows) | 8.61–8.74 s | **0.006 s** |
| page at `OFFSET 7480` | — | 0.018 s |

**Why it sits before R-3 rather than after.** R-3 needs per-occurrence data from
`document_cache.body_text`, and `SearchResult` carries no body field today — body text is
fetched on every row and then discarded (`SearchService.swift:115-129`). Two-phase fetch
changes precisely *when and for which rows* body text is hydrated. Building R-3's
occurrence scanner against the current shape and then re-shaping the fetch underneath it
would mean writing the scanner twice.

**Deliverables.**
- `searchDocuments` split: rank the match into `(docrowid, score)` — filters applied, still
  exact — then join `document_cache` only for the requested window.
- Output parity is the acceptance criterion: same rows, same order, same body text, asserted
  against the current implementation rather than eyeballed.
- Care needed where a filter condition references `dc`: those must stay in the ranking phase
  or the window is drawn from the wrong set. Enumerate every `dc.`-referencing condition in
  `filterConditions` and prove each one lands in phase one.
- This also makes SQL `LIMIT`/`OFFSET` worth using for real, which today no caller does —
  but adopting it is **not** in scope here (it needs the date sort and checklist exclusion
  moved into SQL; see the Q-M2 note in the consolidated plan).

**Data & migration:** none. Query shape only.
**Prereq:** none. **Needs xcodegen:** no.

**Decision point (R-3a-1).** Whether to adopt SQL paging in the same session or leave the
in-memory slice alone. Lean: leave it. The latency win is in the fetch shape, not the
paging, and moving the sort into SQL is a separate behavioural change with its own risks.

**Verify.** Parity test over a spread of query shapes (common term, rare term, phrase,
NEAR, exact, filtered, person-filtered, front-matter-excluded) asserting identical
`IndexedSearchRow` sequences before and after. Then the same eight shapes timed on the
owner's real index.

# Milestone 3 — Signal locators

*Two sessions.* Given a set, find what is distinctive about it. This is where a researcher
discovers vocabulary they could not have guessed.

## S-1 — Keyness *(Effort M)*

**Goal.** Answer "what is *distinctive* about these documents?" rather than "what words are
most common?" Raw frequency gives *the, of, Department*; keyness gives *morale, stiffen,
will to resist* — the actual vocabulary of the argument the alliance report reconstructs.

**Deliverables.**
- Compare the result set's (or working corpus's) term frequencies against corpus baseline
  frequencies, ranked by log-likelihood or log-odds ratio.
- Both halves already exist: `WordFrequencyService` computes per-scope frequencies
  (`corpusTopTerms`, line 178) and Q-3's `fts5vocab` supplies corpus document frequency with
  no scan. The house has already validated the TF-IDF shape at the volume-subject grain —
  `VolumeSubjectProfilesGeneratorCore/ProfileAggregator.swift:156`
  (`ln(corpusDistinctDocs / subjectCorpusDocFreq)`).
- Ships as a **mode** on the existing word cloud (raw frequency vs. keyness), not a new
  screen — same pipeline, same scope resolver (`WordCloudScopeResolver` already resolves
  `.savedSearch`, `.collection`, `.customScope`).
- Statistical honesty: report the measure used, and floor low-frequency terms so a term
  appearing twice cannot top the ranking.

**Data & migration:** none beyond Q-3.
**Prereq:** Q-3.
**Needs xcodegen:** likely no (extends existing word-cloud files).

**Decision point (S-1-1).** Measure: log-likelihood (the corpus-linguistics standard,
comparable to published keyness figures) vs. log-odds ratio with an informative prior
(better behaved for small sets, less familiar). Lean log-likelihood, with the low-frequency
floor doing the work the prior would.

**Verify.** Keyness over the 1948 Western Europe result set should surface the morale
vocabulary — *stiffen*, *morale*, *resist*, *fifth column* — that the alliance report
identifies as the operative argument. If it does not, the floor or the measure is wrong.

## S-2 — Collocation *(Effort M)*

**Goal.** The inverse of NEAR, and its real payoff: not "does X appear near Y" but "**what**
appears near X."

**Deliverables.**
- For a query's hits within the current scope, collect words within ±N tokens of each match
  from `document_cache.body_text`, rank by keyness against the corpus baseline (reuses S-1's
  machinery).
- Window size N is user-adjustable and shares its control vocabulary with Q-1's NEAR
  distance — the same concept, so the same affordance.
- Click a collocate to add it to the query (as a NEAR operand, closing the loop with Q-1).
- **Scope discipline:** compute over the result set, not the corpus. A few thousand
  documents × ~10 KB of body text is tens of MB of scanning — fine on-device; the whole
  corpus is not. Bound it, surface the bound, and stream rather than materialising all text.

**Data & migration:** none.
**Prereq:** S-1 (keyness), Q-1 (for the click-to-query loop).
**Needs xcodegen:** yes.

**Decision point (S-2-1).** Tokenisation for the collocation window: reuse
`WordCloudTokenizer` (consistent with the word cloud, already stopword-aware) vs. a
character-window approach reusing `makeContextSnippet`. Lean `WordCloudTokenizer` — "within
20 *words*" is what a researcher means and what NEAR does.

**Verify.** Collocates of `guarantee` across 1948–49 Western Europe volumes should recover
the *minimum commitment* / *constitutional processes* / *Article 51* cluster the alliance
report reconstructs by hand.

# Milestone 5 — Discovery

*Re-scoped 2026-08-01, after milestones 1–4 shipped (#602–#623). The original text is preserved
in git history; it is replaced rather than annotated because five of its premises are false and
an annotated version would still read as a plan.*

## Why this was re-scoped

Every premise below was checked against shipped code, and several against the live 6.3 GB store
read-only. Five turned out to be false. The pattern is the one this programme has hit repeatedly:
the plan was written before milestones 2–4 existed and describes gaps those milestones filled,
prerequisites that shipped differently, and a model that was never built.

### Premise audit

| Plan claim | Verdict | What is actually true |
|---|---|---|
| D-1 goal: *"nothing in the app helps"* find period vocabulary | **FALSE** | Six shipped surfaces help. The date-range word cloud with the keyness measure answers *"what words did people use for this in 1950"* directly; collocation answers *"what appears near X"*; the concordance shows usage in context. |
| D-1 ①: a vocabulary browse is *"cheap, because the dictionary already exists in the index"* | **PARTLY TRUE** | `frus_documents_vocab` is a persistent `fts5vocab('…','row')` companion created at store open (`FTS5Connection.swift:128-163`). | D-1 ②: stem→surface-forms map is unbuilt and deferred here | **CONFIRMED** | The deferral is recorded in shipped code, not just the plan: `FTS5Vocabulary.swift:60-67` and `QueryInspection.swift:142-152` both name D-1 as owner. ### The organising constraint: the stem ↔ lemma mismatch is real

The FTS5 index is `porter unicode61` **stems** (`FTS5Types.swift:113`, `:126`). The keyness
baseline is NLTagger **lemmas** (`WordCloudTokenizer.swift:114-158`). Measured against the shipped
artifact: `alliance` 15,937, `security` 177,061, `defense` 141,745, `treaty` 204,741 — while the
stems `allianc`, `secur`, `defens`, `treati` are all **absent**.

Two failure modes, and the second is worse:

1. `Keyness.score` turns a missing key into a real zero, which its own doc calls *"a word unique to
   the scope"* — so an unpriceable stem floats to the **top** of the list.
2. `contain` (the verb, 55,794) and `containment` (569) sit side by side as separate lemma keys, so
   the index stem `contain` — which covers *containment* — gets a confident **wrong** denominator.

This is why the repo already refused to unify the two term lists (`BundledKeynessBaseline.swift:24`).
It means: any list of index stems shown to a researcher is unreadable without variants, and any
index stem piped into keyness is wrong. **Deliverable ② is therefore a precondition for ①, not a
follow-on** — and a stem→variants map whose right-hand side is the baseline's own key space is
simultaneously the fix for both.

chunk *outputs* (`SummarizationService.swift:375-418`), which for a classification prompt means
coding a bag of partial label objects, with a silent truncation at the degenerate level (`:407-409`)
— defensible for a summary, not for a code.

### What to do instead

- **(a) Close the provenance leak.** *Effort S, no schema gate.* `GeneratedSummaryExport` has ten
  fields and `authorship` is not among them (`ResearchDataExporter.swift:278-290`); the collection
  exporters got it right (`CollectionExporter.swift:952-965`), so the discipline is achievable and
  silently failed on the next surface built. **This is a live machine/human separation failure in
  the shipped app** and the empirical argument for not giving machine content more surface area.
- **(b) Run background summarization over a working corpus.** *Effort S, no schema gate.*
  `WorkingCorpus.documentKeys` is already the `"volumeId/documentId"` shape
  `SummarizationScope.savedSearch(documentKeys:)` takes. A *structured* prompt already runs across a
  document set, one document per call, persisting a `GeneratedSummary` each with `authorship`
  provenance. This gives the D-2 workflow through the already-attributed path for a call-site
  change — and lets the owner find out empirically whether he wants machine labels before paying
  for them.
- **(c) Tag counts over a working corpus.** Raised in weight by the correction above. The
  distribution D-2 wants already exists as `userTagCounts` on the filter sheet, both platforms; what
  is missing is that same count over a **working corpus** rather than the live match. *Effort S/M,
  no new stored property.* With colleagues already tagging heavily, this is the piece most likely to
  be wanted first.
- **(d) Only if (b) shows he wants them:** a **transient, unstored** proposal in the document view,
  where applying it creates an ordinary `DocumentTagAssignment` he owns. Nothing machine-authored
  persists, so nothing machine-authored can enter a count, an export, or a sync — *"proposal, never
  a finding"* enforced by the storage layer rather than by a chip.

## Found in passing — issues, not sessions

- **`GeneratedSummaryExport` drops `authorship`** — a live provenance leak in the JSON export.
- **The date-range word cloud silently keeps the *earliest* 5,000 documents**
  (`WordCloudScopeResolver.swift:163-178`) with no cap notice, so a "1950s" cloud can describe
  1950–51 and label itself 1950–59. This is the surface that best answers the period-vocabulary
  question, and it is quietly date-biased.
- **iOS has no date-range scope picker in the word cloud** — the block is `#if os(macOS)`.
- **`user_content_vocab` does not exist** (`IndexingPipeline.swift:4855` creates the table with no
  matching vocab DDL), so no vocabulary surface can honestly claim to cover summaries and notes.
- **Porter non-idempotence** affects any surface that hands an index term back to the stemmer;
  undocumented anywhere in the repo.
- **A 10,632-term human-authored period glossary already sits in the `terms` table** (66,095 rows
  across 312 volumes, written by the indexer, read back per-volume only). Existing data, existing
  writer, no cross-volume surface. Overwhelmingly abbreviations, so verify usefulness before
  building.

## Explicitly not in this plan

- **Cloud model routing.** `SummarizationProvider` is already abstracted, so a remote
  provider is architecturally available — but it trades away the "no API key or network
  connection required" property the app currently advertises. Owner decision, not a
  technical one, and out of scope here.
- **Report generation.** Producing prose like the two source reports is not an on-device
  task at any chunking strategy. The app's job is to make the *evidence* assemblable and
  checkable; the writing happens elsewhere.
- **A second, unstemmed FTS5 index.** Q-3's post-filter gets exact-word search correctly
  without doubling index size. Revisit only if profiling shows the post-filter dominating.
- **Re-deriving the corpus from `frus_split.py`-style markdown.** The source reports' Appendix
  A documents a splitter defect filing body prose under `## Notes`. The TEI-native pipeline
  has no such failure mode; provenance here is already better than the corpus those reports
  were built from.
